# Re-measurement of the reworked quarantined detectors

Date: 2026-09-28. Tool: `npm run corpus:resample` (`scripts/resample-unmeasured.ts`).

Six quarantined rules are UNMEASURED because a rework bumped their
`detectorRevision`, which makes the verdicts behind the old measurement stale
(§07). This records what the CURRENT detector finds in the same code, at the
same pinned SHAs, over each rule's own committed file sample.

**These are candidate findings with the code in front of me, not verdicts.**
`tests/corpus/verdicts/README.md` makes a committed verdict immutable, and an
adjudication is a judgement, not a scan.

## The two reworked Python rules

### QA-PY-007 — `pytest.raises` without `match=` · detectorRevision 5

Before the rework, `pythonWithRaisesBlocks` found the raises call by walking a
`with_statement`'s whole subtree and then measured THAT with's block, so a
nested `with pytest.raises(...)` inherited the outer block's statement count
and the single-statement gate — the adjudicated FP core — could never fire.
Seven of eleven adjudicated findings were that shape, because
`pytest-dev/pytest` nests its capture tests inside `with saved_fd(...)`.

After: the call must be a direct context manager of the with it is measured
against, and a single-statement block is exempt regardless of exception type
(the "an unrelated bug raises first" diagnosis needs an earlier line, and a
one-line body has none).

|                               |         |
| ----------------------------- | ------- |
| Sample                        | 5 files |
| Findings                      | 3       |
| Adjudicated **true positive** | 3       |
| Adjudicated false positive    | **0**   |

- `pallets/click tests/test_context.py:655` — three-statement body ending in
  `raise TestException()`. TP.
- `pytest-dev/pytest testing/test_recwarn.py:123` and `:127` — two-statement
  bodies where a `RuntimeError` from the setup line would satisfy the raises.
  TP, and both were already adjudicated.

**0% false positives, down from 9 of 11.** At n=3 this is below
`MEASURED_THRESHOLD = 10`, so the rule stays UNMEASURED until a full corpus
run. That is the correct state, not a gap to be papered over.

### QA-PY-004 — bare truthiness assert on a complex object · detectorRevision 4

Before the rework, revisions 2 and 3 each answered a measured false-positive
cluster by adding that cluster's METHOD NAME to a `predicateRe` list.
`isinstance`, `startswith`, `exists`, `check`, `any`, `all`, `re.match`, and a
dozen more — and ten of the twelve adjudicated findings were still
`exc_info.group_contains(...)` / `excinfo.errisinstance(...)`, neither on the
list. A vocabulary of names is the wrong shape for the fact being expressed:
a call does not pass for "any truthy value", it passes for whatever that call
computed.

After: the gate is structural. A call is exempt; a bare identifier or
attribute chain is not.

|                            |         |
| -------------------------- | ------- |
| Sample                     | 8 files |
| Findings                   | 4       |
| Adjudicated true positive  | 3       |
| Adjudicated false positive | 1       |

- `pallets/click tests/test_basic.py:465` — `assert result_out.exception`.
  TP: any exception satisfies it, including the wrong one.
- `pallets/click tests/test_testing.py:246` — `assert result.exception`, where
  the PREVIOUS line already pins the exact message. TP by the rule's criterion.
  It also exposes a narrow gap: `isGuardFollowedByRealUse` only looks FORWARD,
  so a guard whose precise evidence precedes it is not recognised as a
  supplement.
- `pytest-dev/pytest testing/code/test_code.py:82` — `assert co.path`. TP: any
  non-empty path passes.
- `pallets/click tests/test_termui.py:139` — `assert bar.finished`. **FP.**
  `finished` is a `bool` attribute, and asserting a boolean IS a complete
  check: the wrong value is `False`, and it does not slip through. Detecting
  this needs to know the attribute's type, which a lexical detector does not.

**The one false positive is irreducible for this detector class, and that is
precisely why the rule is in quarantine rather than in `extended`.** The
alternative fixes were both rejected: naming `finished` is the method-vocabulary
mistake this rework removed, and raising the false-positive bar to exclude
attribute chains would abandon the rule's only real capability. At n=4 the
rule stays UNMEASURED; a corpus run at revision 4 is what produces a number
worth acting on.

## A defect the re-sampler had, which is worth recording

The first version of `scripts/resample-unmeasured.ts` returned one sample entry
per VERDICT ROW rather than per distinct file, so a file carrying five verdicts
was fetched and scanned five times and every finding on it was reported five
times. It made QA-PY-007 look like a detector double-fire; a probe with a
corrected line calculation showed all 35 offsets were distinct and the
detector emits one finding per block.

That is the defect this measurement is about, committed into the tool that
measures it: a count inflated by the shape of the bookkeeping rather than by
the code under test. It is fixed, and the comment on `sampleFor` says why.
