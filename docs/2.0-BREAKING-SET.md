# 2.0 Breaking-Set Inventory (preparation only — WI-25)

Source of truth: the strategic blueprint's **§28 Compatibility & Migration**
(plan 1788597687393) and **§18 Suppression Expiry**. This document is the
2.0.0 breaking-set **inventory**: every candidate breaking change, its
benefit>cost justification, and its migration pointer.

**Law (WI-25 acceptance): nothing enters 2.0 "because large".** A breaking
change ships only with (a) owner ratification of this inventory entry and
(b) evidence that `schemaVersion 1` cannot represent the behavior — none
exists today for any frozen surface (blueprint §28). **No entry below is
implemented in this release**; this is the proposal sheet the 2.0 work
consumes.

## The breaking set (justified per blueprint §28)

### BS-1 — Default suppression expiry (blueprint §18)

- **Surface**: `mjolnir.config.json` suppressions (`config.ts` expiry
  semantics).
- **Current contract**: an entry without `expires` never expires; expiry
  evaluated from `expires` only.
- **2.0 change**: entries without explicit `expires` receive a **90-day
  default from entry creation** (creation date captured when the entry is
  first written); **`expires: false`** is the explicit never-expire opt-out.
  Existing hand-written entries without either field keep their behavior
  until edited (no silent retroactive expiry) and are surfaced by
  `mjolnir init`'s config check with a migration suggestion. Expired entries
  suppress nothing and are listed with days-remaining/expired status;
  `suppressionCount` counts active entries only.
- **Why major**: config-key semantics change = major per
  `docs/VERSIONING.md`.
- **Benefit > cost**: debt cannot silently hide regressions.
- **Migration**: `docs/MIGRATION-2.0-DRAFT.md` § BS-1.
- **Status**: PROPOSED — awaiting owner ratification. Not implemented.

### BS-2 — Retirement completion for lapsed deprecations (blueprint §28.2)

- **Surface**: rule registry / `RETIRED_RULE_IDS` (rule lifecycle).
- **Current contract**: detectors whose one-minor deprecation elapsed remain
  registered and fire (some verified downgraded to 100% FP).
- **2.0 change**: full RULE-LIFECYCLE removal of every detector whose
  deprecation window elapsed, into `RETIRED_RULE_IDS` — the set may shrink;
  a smaller high-trust rule set beats a large noisy one.
- **Why major**: rule IDs are immutable; removal of a fired detector from a
  release is a behavior change for every consumer of that rule's findings.
- **Benefit > cost**: the 100%-FP verified set produces noise, not trust;
  retirement is first-class per the rule-evolution law.
- **Migration**: `docs/MIGRATION-2.0-DRAFT.md` § BS-2 (retired-rule list
  published in the CHANGELOG with the 2.0.0 entry).
- **Status**: PROPOSED — awaiting owner ratification. Not implemented.

## Explicitly NOT breaking (blueprint §28.3 — locked defaults)

- **JSON stays `schemaVersion 1`** — additive extension is the default for
  every new field in this plan (`detectorRevision`, run identity,
  `contractVersion`, lifecycle/resolution states, corroboration status,
  artifact identity). No schema v2 exists and none is justified.
- **Exit codes unchanged** — the frozen set in `docs/VERSIONING.md` holds.
- **New verbs/flags additive** — no rename cycles (deprecation cycle per
  `docs/VERSIONING.md`; none planned).
- **Node matrix unchanged** (`engines.node >= 22.18` carries into 2.0
  unchanged unless a separate ratified change says otherwise).
- **Frozen surfaces** — the capability matrix, machine contract, MCP tool
  catalog, and trust artifact formats evolve additively only; the drift
  locks enforce this on every change.

## Publication law

The 2.0.0 migration guide ships **in the CHANGELOG + site** (blueprint §28)
— `docs/MIGRATION-2.0-DRAFT.md` is the working draft that becomes that
guide. Any proposal to break a frozen surface requires evidence that
`schemaVersion 1` cannot represent the behavior; until that evidence exists,
this inventory's NOT-breaking list is binding.
