# QA Doctor 2026

## Quality Intelligence, Evidence & Release Confidence Platform

### The Quality Evidence Engine for Modern Software

---

# Product Vision

QA Doctor is a zero-configuration quality intelligence platform that scans a software repository and answers one fundamental question:

> **What level of software quality can actually be proven for this system — and what evidence supports that claim?**

QA Doctor does **not** primarily answer:

* How many tests exist?
* How high is line coverage?
* How many green checks exist in CI?
* How many QA tools are installed?
* How many rules passed?

Instead, it answers:

* What behavior is actually proven?
* What critical behavior remains unproven?
* How trustworthy are the tests?
* Can the CI result actually be trusted?
* What regressions could reach production undetected?
* What evidence became stale after code changes?
* What quality level can honestly be claimed?
* What should the team do next?

---

# The Core Promise

> **QA Doctor does not tell you how much testing you have.**

> **QA Doctor maps software quality claims to observable evidence.**

> **It distinguishes what is detected, inferred, observed, and verified.**

> **It never allows a score to hide a critical evidence gap.**

> **It prefers uncertainty over false proof.**

Ultimately:

> **QA Doctor answers not only whether your tests pass — but what your software quality can honestly prove.**


must not mean:

```text
Run every test.

```

Instead, it means:

The default scan should prioritize:

2. Deterministic analysis
3. Existing test and coverage evidence

6. Critical path discovery

# 5. Critical Rule: Scores Cannot Hide Critical Failures

This must never happen:

```text
Code Quality:          100
Test Hygiene:          100
Coverage:              100

Authorization:          10
Tenant Isolation:        0

Overall Score:          85
Release:                SAFE
```

Instead:

```text
QUALITY HEALTH

85 / 100

QUALITY LEVEL

A

BUT

RELEASE CONFIDENCE

BLOCKED

Critical evidence missing:

✗ Cross-tenant isolation
✗ Privileged authorization testing
```

A score describes health.

A release verdict describes risk and policy.

The score can never override a critical release gate.

# 6. The Most Important Product Principle

## No Quality Claim Without Evidence

QA Doctor must distinguish between:

```text
TEST EXISTS
```

and:

```text
BEHAVIOR VERIFIED
```

These are not the same thing.

Example:

```ts
it("saves user", async () => {
  await saveUser();

  expect(api.saveUser).toHaveBeenCalled();
});
```

The test may pass even if the real user-saving behavior is broken.

Therefore QA Doctor must analyze:

* What claim is being made?
* What system boundary is relevant?
* What evidence exists?
* Is the evidence relevant?
* Was the behavior actually executed?
* How fresh is the evidence?
* How confident is QA Doctor in the relationship?

---

# 7. False Proof Is More Dangerous Than a False Negative

QA Doctor must operate conservatively.

The following is acceptable:

```text
AUTHORIZATION

Status:
NO SUFFICIENT EVIDENCE

Reason:

A privileged operation was detected,
but QA Doctor could not confidently prove
that existing tests verify negative authorization.
```

The following is dangerous:

```text
AUTHORIZATION VERIFIED
```

when the only evidence is:

```ts
expect(mockGuard).toHaveBeenCalled();
```

Therefore:

> **False negatives may create additional work. False proof can create production risk.**

QA Doctor must prefer:

```text
UNKNOWN
```

over:

```text
VERIFIED
```

when the evidence is insufficient.

# 8. Four Layers of Truth

Every conclusion must declare its source.

## Layer 1 — Detected

A deterministic fact found through repository analysis.

Examples:

```text
Focused test committed.
Skipped test found.
continue-on-error detected.
GraphQL mutation exists.
Authorization guard exists.
Hard sleep found.
```

---

## Layer 2 — Inferred

A relationship inferred from code structure or evidence relationships.

Example:

```text
A privileged operation appears to lack
negative authorization evidence.
```

This is not automatically a defect.

It is an:

```text
EVIDENCE GAP
```

or:

```text
HEURISTIC RISK
```

depending on confidence.

---

## Layer 3 — Observed

A behavior was seen during execution.

Example:

```text
Non-admin identity invoked deleteUser.

Authorization guard executed.

Request rejected.

No database mutation observed.
```

This is stronger than static inference.

---

## Layer 4 — Verified

A claim has sufficient relevant, reproducible, and traceable evidence.

Example:

```text
CLAIM

Non-admin cannot delete users.

VERIFIED EVIDENCE

✓ Relevant operation identified
✓ Non-admin identity used
✓ Authorization boundary executed
✓ Operation rejected
✓ Protected data unchanged
✓ Execution captured
✓ Evidence linked to current commit
```

Only this level may support:

```text
VERIFIED
```

claims.

# 9. Evidence Levels

Every important behavior receives an evidence classification.

## E0 — No Evidence

```text
No relevant automated or runtime evidence exists.
```

---

## E1 — Weak Evidence

Examples:

```text
Mock-only verification.
Implementation-coupled test.
Indirect evidence.
Low-confidence structural relationship.
```

---

## E2 — Partial Evidence

Example:

```text
Happy path verified.

Negative cases missing.
```

---

## E3 — Strong Evidence

```text
Positive and negative behavior verified
at the relevant system boundary.
```

---

## E4 — High Confidence

```text
Behavior verified across:

✓ Relevant boundary
✓ Positive path
✓ Negative path
✓ Authorization where relevant
✓ Failure handling where relevant
✓ Data integrity where relevant
✓ Runtime execution
✓ CI gate
```

E4 should not mean "perfect software."

It means:

> **The specific quality claim has strong, multi-dimensional evidence.**

# 13. Static Analysis Is a Discovery Engine

AST analysis is essential, but it is not universal proof.

QA Doctor should use static analysis to discover:

* REST endpoints
* GraphQL queries
* GraphQL mutations
* Controllers
* Resolvers
* Guards
* Roles
* Permissions
* Tenant identifiers
* Database operations
* Transactions
* Retries
* External dependencies
* Tests
* Assertions
* Mocks
* CI workflows
* Coverage configuration

Static analysis can reliably detect many facts.

However, it cannot always prove:

* Database rollback behavior
* Transaction leakage
* Retry exhaustion
* Race conditions
* Actual network failure behavior
* Actual authorization enforcement
* Cross-service behavior
* Cache invalidation
* Queue ordering
* Runtime side effects

Therefore:

```text
STATIC ANALYSIS
        ↓
DISCOVER
        ↓
INFER
        ↓
IDENTIFY EVIDENCE GAP
        ↓
OBSERVE RUNTIME
        ↓
VERIFY
```

QA Doctor must always disclose which stage produced the conclusion.

# 21. Finding Taxonomy

Every finding must have a primary classification.

## A. Deterministic Defect

A concrete invalid or dangerous pattern was found.

Example:

```text
continue-on-error masks a failing required test.
```

---

## B. Evidence Gap

QA Doctor cannot find sufficient evidence for an important claim.

Example:

```text
Privileged operation lacks negative authorization evidence.
```

This does **not** necessarily mean authorization is broken.

It means:

> QA Doctor cannot currently prove that the behavior is correct.

---

## C. Heuristic Risk

A probabilistic pattern may reduce quality.

Examples:

```text
Potential excessive mocking.
Potential implementation coupling.
Potential brittle snapshot.
Potential test ordering dependency.
```

---

## D. Observation

Informational fact.

Example:

```text
Mutation report is 14 days old.
```

The UI, score engine and release policy must treat these categories differently.
