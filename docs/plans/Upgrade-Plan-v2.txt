# PART 1 — MULTI-LANGUAGE SUPPORT

## 1.1 The Architecture Change That Makes It Possible

The current engine is regex-based over JS/TS. Multi-language requires one
structural refactor first — **the Language Adapter interface**:

```ts
interface LanguageAdapter {
  id: string;                          // 'typescript' | 'python' | 'java' ...
  extensions: string[];                // ['.ts', '.py', '.java']
  /** Parse once, share across rules (tree-sitter or native parser). */
  parse(text: string): ParsedFile;
  /** Framework detection per language (pytest.config, pom.xml, ...). */
  detectFrameworks(root: string): string[];
  /** Canonical test-file discovery per ecosystem conventions. */
  isTestFile(path: string): boolean;
}

interface UniversalRule {
  meta: RuleMeta;
  /** Rules declare which adapters they support. */
  appliesTo: string[];                 // adapter ids
  run(ctx: { file: string; ast: ParsedFile; text: string }): Finding[];
}
```

Key decisions:
- **Parser: tree-sitter grammars** — one consistent AST API across all
  languages, incremental, battle-tested (used by GitHub itself).
  Alternative rejected: per-language native parsers (jest/pytest) = N
  integrations instead of 1.
- **Rules become language-aware, not duplicated**: `no-assertions` exists
  in every ecosystem; `continue-on-error` is GitHub-only; `pytest.raises`
  misuse is Python-only. The rule registry maps rules → languages.
- **Scoring unchanged** — deductions are universal; dimensions gain a
  language axis.

## 1.2 Language Rollout Order (by market pull, not by ease)

| Phase | Language | Test ecosystems | Why this order |
|---|---|---|---|
| L0 (done) | TypeScript/JS | Jest, Vitest, Playwright | Core |
| L1 | **Python** | pytest, unittest, Playwright-Python | Biggest QA community; pytest is the world's most-used test runner |
| L2 | **Java/Kotlin** | JUnit 5, TestNG, Selenium, Playwright-Java | Enterprise QA stronghold |
| L3 | **Go** | testing pkg, testify, Ginkgo | Fast-growing; small rule surface = quick win |
| L4 | **C#/.NET** | xUnit, NUnit, MSTest, Playwright-.NET | Enterprise; large but slower-moving |
| L5 | **Rust / Ruby** | cargo-test/RSpec | Community demand driven |

Per-language effort estimate: ~3–4 weeks each (adapter + ~15 core rules +
fixtures + framework detection). Python first.

## 1.4 What Stays Universal vs Per-Language

```text
UNIVERSAL (write once):
  scorer · JSON contract · exit codes · --scope changed (git layer)
  CI integrity engine · suppressions/config · reporters · fuzz harness

PER-LANGUAGE (adapter + rules):
  parser · test-file discovery · framework detection
  test-quality rules · hygiene rules · fixtures
```

## 2.3 Layer 3 — Runtime Evidence (post-static, ~6 weeks)  🟡 PARTIAL — lighter tier than planned

The bridge to Product.txt's Evidence Graph, scoped tightly to Playwright:

1. **Trace-based flakiness evidence** — parse Playwright trace.zip files:
   which tests retried, network failures during test, console errors.
   `qa-doctor traces ./test-results/` → reliability report per spec.
   ⬜ NOT BUILT — `forensics` command parses the Playwright **JSON reporter**
   output instead, no `trace.zip` parsing code exists.
2. **Retry forensics** — a test that passes only on retry gets flagged
   with its trace attached: *this is not a passing test, it's a lucky test.*
   ✅ SHIPPED, but sourced from JSON reporter retry counts, not the trace itself.
3. **Coverage of app code during e2e** — consume Playwright's coverage
   output → "your e2e suite exercises 34% of src/" (honest framing:
   executed-by, not verified-by). ⬜ NOT BUILT.

Sequencing decision (§1.5): **Playwright Deep Mode BEFORE Java**.
Rationale: differentiation compounds — owning the Playwright niche drives
adoption harder than being the 5th JUnit linter. Python stays first
(bigger community), then Playwright Deep, then Java.

## 2.4 Distribution Strategy for the Playwright Push

1. **`qa-doctor doctor:playwright`** — dedicated subcommand; one command
   that runs ONLY the PW families. Shareable, screenshot-able output.
2. **GitHub Action recipe** in Playwright's own docs ecosystem (PR to
   their examples repo).
3. **Content engine**: "The Playwright Anti-Pattern Catalog" — one blog
   post per rule family, each ending with the CLI one-liner that detects it.
4. **VS Code extension (later)**: inline warnings using the same JSON contract.

# ANTI-CREEP GUARDRAILS (unchanged law)

* Every new rule ships with must-fire/must-not-fire fixtures — no exceptions.
* Every new language needs a real-world corpus (10+ OSS repos) audited
  for false positives before GA of that adapter.
* The deferred ledger absorbs anything not listed above.
