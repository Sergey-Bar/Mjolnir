# P0 — Ship blockers

The published product is broken right now.

### B-1 · `npx mjolnir-qa@latest` is broken on Linux and macOS

- **Evidence:** `npm view mjolnir-qa version` → **`0.4.0`**. `dist-tags.latest = 0.4.0`.
  0.4.0 is the release whose `dist/cli.mjs` has no shebang — the bug the
  0.5.0 PR fixed. The README's headline command is `npx mjolnir-qa@latest`.
- **Impact:** every first-time user on Linux/macOS gets `import: not found`.
  This is the whole funnel.
- **Blocked by:** B-2.

### B-2 · The Release workflow fails at `npm publish` on every tag push

- **Evidence:** run `33265358816` (v0.5.0), step _Publish to npm (OIDC
  trusted publishing)_:
  ```
  npm http fetch POST 404 .../oidc/token/exchange/package/mjolnir-qa
  npm verbose oidc  OIDC token exchange error - package not found
  npm error code ENEEDAUTH
  ```
  The OIDC token _was_ minted (the id-token GET returned 200) — the
  registry rejected the exchange. Five consecutive tag pushes failed the
  same way (`33264866240`, `33265101424`, `33265255744`, `33265358816`).
- **Root cause:** the trusted-publisher entry on npmjs.com was never
  created. `.planning/STATE.md` already lists it as manual step #1; it is
  still open. Four workflow commits (`c9260d1`…`be0a3bc`) tried to fix
  from the repo side a problem that has no repo-side fix.
- **Fix:** either (a) create the Trusted Publisher on npmjs.com
  (GitHub Actions · `Sergey-Bar` · `Mjolnir` · `release.yml` · environment
  **blank**), or (b) stop fighting OIDC — add `NPM_TOKEN` as a repo secret
  and publish with `--provenance` and `NODE_AUTH_TOKEN`. Option (b) works
  today and takes 5 minutes.
- **Size:** S (config), then re-tag.

### B-3 · A GitHub Release exists for a version that is not on npm

- **Evidence:** `gh release list` → `v0.5.0 · Latest`. npm → `0.4.0`.
  In `release.yml` the `softprops/action-gh-release` step runs **before**
  the publish step, so a failed publish still leaves a public Release
  advertising a version nobody can install.
- **Fix:** move the GitHub Release step after a successful `npm publish`,
  or add `if: success()` chaining. Add a post-publish verification step
  (`npm view mjolnir-qa@$VERSION version`) so the job cannot go green
  without the package actually being live.
- **Size:** S.

### B-4 · `0.4.0` is on npm with no matching git tag

- **Evidence:** `git tag -l` → `…v0.3.7`, `v0.5.0`. No `v0.4.0`. But
  `npm view mjolnir-qa time.created` → 0.4.0 published 2026-08-27.
- **Impact:** the currently-installable version is not reproducible from
  the repo. For a tool whose pitch is verifiable trust, that is the wrong
  gap to have.
- **Fix:** tag the commit 0.4.0 was built from, or publish 0.5.0 and
  deprecate 0.4.0 on npm.
- **Size:** S.

# P1 — Honesty defects

Cases where the tool reports something that is not true. For this product
these are not cosmetic — they are the category of bug it exists to find in
other people's suites.

### H-1 · `--strict` fails CI on a rule the project itself measured at 100% false positives

- **Reproduction** (a throwaway repo with one `conftest.py` and one file):
  ```python
  # test_sample.py
  def test_placeholder():
      pass
  ```
  ```
  mjolnir . --strict --json  → exit 1, score 60
  QA-PY-003 : error : E2
  QA-PY-006 : error : E2 : measuredFpRate = 1
  ```
- **The contradiction:** `QA-PY-006` carries `evidenceLevel: "E2"` — the
  _highest_ evidence level, the one the docs reserve for proven
  deterministic defects — while `docs/FP-AUDIT.md` records its measured
  false-positive rate as **100% (n=19, 0 TP)**. Both numbers ship in the
  same JSON object, on the same finding, and nothing reconciles them.
- **Also affected:** `QA-CS-106`, `QA-CS-108`, `QA-CS-111`, `QA-JV-106`,
  `QA-JV-108`, `QA-JV-111` — all 100% measured FP. `QA-JV-103` (50%) is
  quarantine **and** `severity: "error"`.
- **Fix:** make the tier authoritative over severity and evidence.
  Quarantine ⇒ severity capped at `info`, evidence forced to `E0`, and
  therefore never gating (`isAdvisoryFinding` already excludes E0). Assert
  it in `doctor`: no quarantine rule may emit `error`.
- **Size:** M. **This is the highest-value single fix in the repo.**

### H-2 · Law #3 is documented as executable and is not enforced

- **Evidence:** `mjolnir doctor` →
  ```
  ✓ tier-enforcement
      57/60 core rules unmeasured (informational until majority classified)
  Mjölnir self-audit: WORTHY        (exit 0)
  ```
  `CLAUDE.md`: _"Rules without a measured FP rate (n ≥ 10) cannot ship in
  the core tier."_ 57 of 60 do exactly that, and the check marks itself ✓.
- **Impact:** the repo's own headline governance mechanism is decorative.
  `docs/FP-AUDIT.md` states the same thing correctly ("76 rules carry no
  measured FP rate. Any of them in the core tier is shipping on an
  unverified assumption") — so the docs are honest and the _enforcement_ is
  not, which is the worse way round.
- **Fix:** pick one and make it true. Either (a) restate the law as a
  target with a dated deadline and a ratchet (`MAX_UNMEASURED_CORE`, lowered
  every release, `doctor` fails when exceeded), or (b) demote unmeasured
  rules to `extended` until measured. (a) is realistic; (b) is honest but
  empties the core tier.
- **Size:** S for the ratchet, L for the classification work behind it (see M-1).

### H-3 · `--max-duration` does not bound the scan

- **Reproduction:** one 891 KB spec file, `mjolnir . --max-duration 2` →
  **26.1 s wall clock**, and the JSON says:
  ```json
  {
    "partial": true,
    "analysisStatus": {
      "discovery": "partial",
      "rules": "complete",
      "skippedFiles": 0,
      "durationMs": 25867
    }
  }
  ```
- **Three separate defects in one line:**
  1. The deadline is only checked inside the discovery walk. The rule loop
     in `runScan` (`src/cli.ts:281`) never checks it, so the budget
     cannot be honoured.
  2. `analysisStatus.discovery` is derived from `Date.now() > deadline`
     (`src/cli.ts:427`) — discovery finished completely, and is reported
     `"partial"`.
  3. `analysisStatus.rules` is the string literal `"complete"`
     (`src/cli.ts:428`). It can never say anything else.
- **Fix:** check the deadline per file in the rule loop; count unscanned
  files into `skippedFiles`; derive both `analysisStatus` fields from what
  actually happened. Help text (`--max-duration <sec> stop analysis after N
seconds`) then becomes true.
- **Size:** M.

### H-4 · A nonexistent scan target exits 0

- **Reproduction:**
  ```
  mjolnir ./does-not-exist-xyz   → exit 0
  mjolnir ./some-file.txt        → exit 0
  ```
  Both print the empty-state box and exit clean.
- **Impact:** a typo'd path in a CI step is a silent green. That is a
  false proof of verification — the exact failure mode this product sells
  against.
- **Fix:** validate the target in `runScanCommand`: missing → exit 10 with
  the path; a file rather than a directory → exit 10. Keep exit 0 only for
  a real directory that genuinely has no tests.
- **Size:** S. **Highest value-per-line fix in the repo.**

### H-5 · The empty-state hint recommends a flag that does not exist

- **Evidence:** `src/reporter/terminal.ts:328` prints
  `If your tests live elsewhere: mjolnir --tests-dir <path>`.
  `grep -rn "tests-dir" src/` returns that one line and nothing else.
  `mjolnir --tests-dir .` → **exit 10**, usage error.
- **Impact:** every user who hits the empty state — i.e. every user whose
  layout the tool did not understand, the one moment they need help — is
  sent to a flag that rejects them.
- **Fix:** implement `--tests-dir`, or change the line to
  `mjolnir <path-to-your-tests>`.
- **Size:** S.

### H-6 · The empty-state message names only three JS frameworks

- **Evidence:** `src/reporter/terminal.ts:321` —
  `"No Jest/Vitest/Playwright test files were found."` The tool ships
  adapters for Python, Java, C# and GitHub Actions, and the README leads
  with "All four Playwright bindings".
- **Fix:** list what was actually searched for per adapter.
- **Size:** S.

### H-7 · `config.gate` is validated, documented, and never read

- **Evidence:** `QADoctorConfig.gate` is declared (`src/config/config.ts:20`)
  and validated with a fail-fast error (`config.ts:50`). The exit-code
  decision (`src/cli.ts:700`–`705`) is hardcoded:
  ```ts
  return result.findings.some(
    (f) => f.severity === "error" && !isAdvisoryFinding(f),
  )
    ? 1
    : 0;
  ```
  `grep -rn "gate" src/` shows no other consumer.
- **Impact:** `"gate": "warning"` in a user's config is accepted, validated,
  and does nothing. A rejected value even produces a hard error — which
  tells the user the field is live.
- **Fix:** wire it into the exit-code decision, or delete the field and its
  validation.
- **Size:** S.

### H-8 · Discovery silently truncates at 10 000 files with no `partial` flag

- **Evidence:** `src/adapters/typescript.ts:113`, `python.ts:109`,
  `java.ts:117`, `csharp.ts:114` — all four:
  ```ts
  if (Date.now() > deadline || out.length > 10_000) return;
  ```
  No `onSkipped()` call, so `skippedFiles` stays 0 and `partial` stays
  false. `out` is the **shared** `ctx.testFiles`, so the cap is global
  across adapters: on a large monorepo the TypeScript adapter (which runs
  first) can consume the entire budget and Python/Java/C# discover
  **nothing**, silently.
- **Fix:** per-adapter budgets, `onSkipped()` on truncation, and a named
  reason in `analysisStatus`.
- **Size:** M.

### H-9 · `--scope changed` only sees TypeScript/JavaScript changes

- **Evidence:** `src/scope/changed.ts:74`:
  ```ts
  if (file && /\.(spec|test)\.(ts|js|tsx|jsx|mjs|cjs)$/.test(file))
  ```
  `test_*.py`, `*Test.java`, `*Tests.cs` and `.github/workflows/*.yml` are
  never added to `changedFiles`, so `filterToChanged` drops every finding
  on them (`!lines → return false`).
- **Impact:** `mjolnir --scope changed` is what `--help` and the README
  present as _the_ product ("The product is one command in CI"). On a
  Python, Java or C# repo it reports clean no matter what the PR does.
- **Fix:** derive the predicate from `ADAPTERS[].isTestFile` instead of a
  duplicated literal.
- **Size:** S. **High impact for the size.**

### H-10 · `--scope changed` misses uncommitted work and hardcodes `main`

- **Evidence:** `computeChangedScope(root, baseBranch = "main")` diffs
  `mergeBase..HEAD` only; `runScan` calls it with no base argument
  (`src/cli.ts:333`), and no CLI flag exists to set one.
- **Impact:** (a) running it locally before committing reports nothing;
  (b) on a `master`-named repo every lookup fails, `degraded` is set, and
  `filterToChanged` returns **all** findings — so `--scope changed`
  silently becomes a full scan. Honest (the reason is reported) but
  surprising in CI.
- **Fix:** add `--base <ref>`, fall back `main → master → origin/HEAD`, and
  include the working tree (`git diff HEAD`) when scanning locally.
- **Size:** M.

# P2 — Reliability and robustness

### R-1 · A read-only scan writes into the scanned repository

- **Evidence:** after `node dist/cli.mjs .`, `git status --short` shows
  `M .mjolnir/stats.json`. The write happens in the milestone block
  (`src/cli.ts:684`–`693`), on an ordinary scan.
- **Impact:** every scan dirties the working tree — including CI's own
  self-scan step, and any pipeline with a `git diff --exit-code` guard.
- **Fix:** write stats only from commands that own them (`diff`), or gate
  behind an explicit opt-in.
- **Size:** S.

### R-2 · `saveStats` is unguarded — a read-only filesystem crashes the scan

- **Evidence:** `src/commands/stats.ts:145` — bare `mkdirSync` +
  `writeFileSync`, no try/catch. Callers (`runScanCommand`,
  `runDiffCommand`) wrap in a catch that returns **exit 20 (internal
  error)**.
- **Impact:** scanning a read-only mount (a common container pattern,
  `docker run -v $PWD:/src:ro`) turns a successful analysis into a crash
  _after_ all the work is done.
- **Fix:** best-effort write; degrade to a warning.
- **Size:** S.

### R-3 · `.mjolnir/` state files are half-tracked

- **Evidence:** `git ls-files .mjolnir/` → `.mjolnir/stats.json` (tracked,
  and modified by every scan — see R-1). `.mjolnir/baseline.json` is
  untracked _and_ not in `.gitignore` → shows up as `??` after any
  `mjolnir baseline`.
- **Fix:** decide per file. `stats.json` is machine-local → ignore it.
  `baseline.json` is meant to be committed (the `mjolnir.yml` workflow
  fetches it from the base branch) → track it deliberately.
- **Size:** S.

### R-4 · `mjolnir fix` rewrites `.only` inside strings and comments

- **Evidence:** `src/commands/fix.ts:101` — `stripDotOnly` runs
  `text.replace(/\b(test|it|describe|bench)\.only\s*\(/g, "$1(")` over the
  **raw whole file**. The `codeText` masking layer that the whole Phase-1
  FP firewall is built on is not used anywhere in `fix.ts`.
- **Impact:** a fixture, a snapshot, a docs example or an assertion like
  `expect(src).toContain("it.only(")` is silently rewritten. For a tool
  that markets "Safe Auto-Fix with Proof", editing test data is the worst
  possible failure.
- **Fix:** locate the edit via `codeText` (or the finding's line/column)
  and apply a ranged edit, not a global replace.
- **Size:** M.

### R-5 · `fix` loses file permissions and leaks temp files

- **Evidence:** `src/commands/fix.ts:251`–`252` — `writeFileSync(tmp,
text); renameSync(tmp, abs)`. The temp file is created with the default
  mode, so on POSIX a `0600` or executable file comes back `0644`. If
  `renameSync` throws, `${abs}.mjolnir-tmp` is left on disk (the catch does
  not unlink it), and a `*.mjolnir-tmp` file will be picked up by watchers
  and by `git status`.
- **Fix:** `statSync` the original first and `chmodSync` the temp to match;
  unlink the temp in the catch.
- **Size:** S.

### R-6 · `fix --dry-run` reports every planned fix as a failure

- **Evidence:** `src/commands/fix.ts:215` pushes
  `status: "failed"` with `"(dry-run: not applied)"`; `renderFixReport`
  renders `failed` with a ✗ and the summary reads
  `0 applied · N not applied`. A successful dry run looks like a broken
  tool.
- **Fix:** add a `"planned"` status with its own icon and summary line.
- **Size:** S.

### R-7 · Path containment is prefix-based, so symlinks escape it

- **Evidence:** `src/commands/fix.ts:57` — `abs.startsWith(root)` with no
  `realpathSync`. A symlink inside the scan root pointing at
  `~/.ssh/config` resolves to a contained path and is written through.
  `cli.ts` already imports `realpathSync` for `isEntryPoint`, so the
  primitive is at hand.
- **Note:** the discovery walkers _do_ skip symlinks
  (`entry.isSymbolicLink() → continue`), which limits the blast radius to
  plugin-supplied finding paths — the exact case the guard was written for.
- **Fix:** `realpathSync` both sides before the prefix check.
- **Size:** S.

### R-8 · Ignore state is module-global mutable

- **Evidence:** `src/discovery/ignores.ts:77`–`78` — `cachedRoot` /
  `cachedExtraPatterns` at module scope; `initIgnores` early-returns when
  the root matches; `isDefaultIgnored` reads the globals. A
  `_resetIgnoresForTests()` export exists, which is the tell.
- **Impact:** scanning two roots in one process (library use, the corpus
  audit, any future watch mode) silently applies the first root's
  `.mjolnirignore` to the second.
- **Fix:** pass a resolved ignore matcher through `ScanContext`.
- **Size:** M.

### R-9 · 97 bare `catch {}` blocks with no way to see what was swallowed

- **Evidence:** `grep -c catch src/**/*.ts` → 97, the large majority
  `} catch {`. Rule crashes are swallowed per file in every adapter's
  `runRules` ("Crash isolation (§25)") without incrementing any counter —
  a rule that throws on every file of a repo is indistinguishable from a
  rule that found nothing.
- **Fix:** a `--debug` flag that prints swallowed errors, and a
  `rulesCrashed` counter in `analysisStatus`.
- **Size:** M.

### R-10 · `.mjolnirignore` claims gitignore syntax and is not

- **Evidence:** the file's own header says _"Same glob syntax as
  .gitignore"_. `globToRegExp` (`ignores.ts:136`) anchors `^…$` against the
  full relative path, supports only `*`, `**`, `?`, and has no `!`
  negation. `node_modules` on a line matches nothing; gitignore users
  expect it to match at any depth.
- **Fix:** implement the two gitignore behaviours people actually rely on
  (bare-name-at-any-depth, `!` negation) or correct the comment and the docs.
- **Size:** M.

# P3 — Security and supply chain

### S-1 · Four permanently-red workflows on every commit

`gh run list` on `be0a3bc` — same result on the three commits before it:

| Workflow                      | Status | Cause                                                                                                                                                                                                                      |
| ----------------------------- | ------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| trivy                         | ❌     | `docker build` on a `Dockerfile` that does not exist: `failed to read dockerfile: open Dockerfile: no such file or directory`. Unedited GitHub template — it scans a container image; this project ships an npm package.   |
| ESLint                        | ❌     | Installs `eslint@8.10.0` against a repo on eslint 10 → `ERESOLVE`. Also passes `--config .eslintrc.js`, which does not exist (the repo uses flat `eslint.config.js`). Redundant: `npm run lint` in `ci.yml` already gates. |
| Microsoft Defender For Devops | ❌     | Requires Azure onboarding that was never done; pins `dotnet 5.0.x` (EOL).                                                                                                                                                  |
| Release                       | ❌     | See B-2.                                                                                                                                                                                                                   |

- **Impact:** four red X's on every commit of a repo whose product is

  reading CI status — which is how the next real failure gets missed.
- **Fix:** delete trivy/eslint/defender (each is either redundant or
  inapplicable), or convert trivy to `scan-type: fs` and fix the eslint job
  to `npm ci && npx eslint .`. CodeQL and OSV-Scanner are green and doing real
  work; Semgrep is green and doing none (see S-9).
- **Size:** S.

### S-2 · `codeql.yml` references `actions/checkout@v7`

- **Evidence:** `.github/workflows/codeql.yml:60`. No such major version
  exists. The job currently passes because that step sits in a path that
  is not reached, but it is a live landmine.
- **Size:** S.

### S-3 · No `permissions:` block in `ci.yml`, `release-smoke.yml`, `corpus-audit.yml`

- **Evidence:** `grep -rn "permissions:" .github/workflows/` — those three
  are absent, so they inherit the repository default, which may be
  read-write for all scopes.
- **Fix:** `permissions: contents: read` at the top of each.
- **Size:** S.

### S-4 · No action is pinned to a SHA

- **Evidence:** `actions/checkout@v4`, `actions/setup-node@v4`,
  `actions/upload-artifact@v4`, `actions/github-script@v7`,
  `softprops/action-gh-release@v2`. `osv-scanner`, `trivy-action` and
  `semgrep-action` _are_ SHA-pinned — so the convention exists and is
  applied inconsistently, and the un-pinned ones include the two that
  handle the release (`gh-release`) and the PR token (`github-script`).
- **Fix:** pin all to SHA with a `# vX.Y.Z` comment; Renovate is already
  configured and understands pinned digests.
- **Size:** S.

### S-5 · `mjolnir.yml` interpolates event data into a shell step

- **Evidence:** `.github/workflows/mjolnir.yml:26`–`27` —
  `git fetch origin ${{ github.event.pull_request.base.ref }}`.
- **Risk today:** low — `base.ref` is a branch in the _base_ repo, not
  fork-controlled. It is still the pattern static analysers flag, and it is
  the pattern this project's own QA-CI family exists to catch in other
  people's workflows.
- **Fix:** pass through `env:` and reference `"$BASE_REF"`.
- **Size:** S.

### S-6 · `mjolnir.yml` cannot post its comment on fork PRs

- **Evidence:** the job declares `pull-requests: write`, but on a
  `pull_request` event from a fork the `GITHUB_TOKEN` is read-only. The
  `actions/github-script` step will 403.
- **Fix:** either accept it and add `continue-on-error: true` on the
  comment step with a Job-Summary fallback, or move to the
  `workflow_run` pattern. Do **not** switch to `pull_request_target`.
- **Size:** S.

### S-7 · No `timeout-minutes` on any job except `corpus-audit`

- **Impact:** a hung `npm ci` or a hung scan sits for GitHub's 6-hour
  default across a 3-OS matrix.
- **Fix:** `timeout-minutes: 20` on `build-test`, 10 on the rest.
- **Size:** S.

### S-8 · Plugins execute arbitrary code and the report never says so

- **Evidence:** `src/plugins/load.ts` — documented no-sandbox model,
  `require(decl.package)` with full Node privileges. The reserved-prefix
  guard and the `QA-PLUGIN-000` degradation path are good. What is missing:
  a **successful** plugin load is invisible in the output.
- **Fix:** print `Plugins: <name>@<version> (N rules)` in the scan footer
  and include it in the JSON. A reader of a scan report should be able to
  tell whether third-party code ran.
- **Size:** S.

### S-9 · Semgrep is green and scans nothing

- **Evidence:** run `33265354892` is ✅ green. Inside it:
  ```
  === Running: semgrep scan --sarif --output=semgrep.sarif     (0.06 s, no --config)
  === Running: semgrep ci
  run `semgrep login` before using `semgrep ci` or set `--config`
  ```
  The job reported success anyway. `gh api .../code-scanning/analyses`
  confirms the outcome: **`Semgrep — 0 results`** on every run, because an
  empty SARIF is what gets uploaded.
- **Contributing:** `returntocorp/semgrep-action` is the pre-rename,
  deprecated action (its own log prints a deprecation notice dated 2022);
  `publishDeployment` is not a valid input (`##[warning] Unexpected
input(s) 'publishDeployment'`); and `gh secret list` is **empty**, so
  `SEMGREP_APP_TOKEN` does not exist.
- **Impact:** this is worse than the four red workflows in S-1. Red is
  honest. A green check mark on a scanner that ran zero rules is a false
  green in the repo's own CI — the exact pattern the `QA-CI` rule family
  exists to catch in other people's workflows. The Security tab currently
  shows a clean Semgrep result that means nothing.
- **Fix:** delete it (CodeQL covers the same SAST ground and is real — see
  below), or replace with the current action and an explicit ruleset:
  `semgrep/semgrep-action` with `config: p/typescript p/security-audit`,
  and fail the step when the scan itself errors.
- **Size:** S.

### S-10 · The repo's own CodeQL alerts have been open and unactioned

- **Evidence:** `gh api repos/Sergey-Bar/Mjolnir/code-scanning/alerts?state=open`
  returns **5 open medium alerts**, all `actions/missing-workflow-permissions`:
  `ci.yml:14`, `ci.yml:41`, `corpus-audit.yml:14`, `release-smoke.yml:16`,
  `defender-for-devops.yml:32`.
- **Note:** this is independent confirmation of **S-3** — CodeQL found it
  first, and nobody read the Security tab. Worth stating plainly: CodeQL is
  the one security workflow here doing real work (`javascript-typescript`,
  5 results per run) and its output is being ignored.
- **Fix:** fix S-3; four of the five alerts close. Deleting
  `defender-for-devops.yml` (see S-1) closes the fifth.
- **Size:** S.

# P4 — Performance

### P-1 · Scan time is quadratic in file size

Measured, one file per run, `dist/cli.mjs`:

| Input                        | Size   | Wall clock  |
| ---------------------------- | ------ | ----------- |
| whole repo (105 test files)  | —      | 1.36 s      |
| one synthetic spec           | 297 KB | 3.78 s      |
| the same, 3× longer          | 891 KB | **26.14 s** |
| 50 KB of unterminated quotes | 50 KB  | 2.20 s      |

3× the input, ~7× the time. The default file cap is 1 MB
(`LIMITS.maxFileBytes`), so a single file _inside_ the allowed range costs
~30 s. Generated or bundled spec files hit this immediately.

- **Fix:** profile (the masking layer and the per-rule global regex
  re-scans are the likely suspects); add a per-file time budget that skips
  and reports, and make it feed `skippedFiles` honestly. Pairs with H-3.
- **Size:** M–L.

### P-2 · The repository tree is walked four times

- **Evidence:** `discoverTestFiles` in each of `typescript.ts`,
  `python.ts`, `java.ts`, `csharp.ts` calls its own `walk*` from
  `ctx.workspace.root`. Every walk `readdirSync`s every directory, and per
  directory also calls `isLintFixtureDir(full)` — **another** `readdirSync`.
  So ~8 directory reads per directory per scan.
- **Evidence (allocation):** `isDefaultIgnored` (`ignores.ts:52`) calls
  `globToRegExp(pattern)` inside a `.some()` — a fresh `RegExp` compiled
  per pattern per path. ~25 default patterns × every path × 4 walks.
- **Fix:** one shared walk that dispatches each file to the adapter that
  claims it; memoise the compiled globs and the fixture-dir check.
- **Size:** M.

# P5 — Measurement and product debt

### M-1 · 47% of the corpus verdict backlog is unclassified

- **Evidence:** `tests/corpus/verdicts/*.jsonl` — 576 lines, **271** with
  `"verdict": ""`. `docs/FP-AUDIT.md`: _"Coverage: 15/91 rules measured
  (16%)"_.
- **Impact:** this is the bottleneck behind H-1 and H-2. Nothing else moves
  until it does.
- **Fix:** it is human work with a defined process
  (`tests/corpus/review/<RULE-ID>.md` → fill `verdict` → `npm run
fp-audit:generate`). Sequence it: the 7 core rules that fire most often
  first, then `QA-TEST-004` on `tanstack-query` (157 findings).
- **Size:** L, and it is the one that matters.

### M-2 · Seven rules have never produced a true positive

- **Evidence:** `docs/FP-AUDIT.md` — `QA-CS-106`, `QA-CS-108`,
  `QA-CS-111`, `QA-JV-106`, `QA-JV-108`, `QA-JV-111` at 100% FP (n=20 each,
  **0 TP**), `QA-PY-006` at 100% (n=19).
- **Decision needed:** retire them (rule IDs are immutable but a rule can
  be removed from `RULES`), or rewrite the detection. Shipping seven rules
  that have provably never been right — even behind `--strict` — is a
  standing liability, and per H-1 three of them can fail a build.
- **Size:** M per rule.

### M-3 · Nothing measures false negatives

- **Evidence:** the north-star metric in `CLAUDE.md` is "false-proof rate
  ≈ 0", measured only as FP rate. There is no recall corpus and no
  must-fire measurement outside the single-example fixtures.
- **Symptom worth investigating:** the self-scan finds **0** findings
  across 105 test files and 1246 test declarations (1 finding under
  `--strict`). That may be a genuinely clean suite, or it may be that the
  rule set rarely fires on ordinary unit-test code. Today there is no way
  to tell those apart, which means the FP-rate discipline is optimising one
  side of a two-sided problem.
- **Fix:** seed the corpus repos with known-bad commits (revert a real
  `.only` fix, re-add a removed `sleep`) and lock the recall count the same
  way `COUNT-LOCK.md` locks the FP count.
- **Size:** L.

### M-4 · `NORMALIZATION_K` is unfitted

- **Evidence:** `src/scorer/scorer.ts:107` — _"NORMALIZATION_K remains
  unfitted. A corpus fit … is outstanding work."_ Correctly disclosed;

- **Size:** M (now that 13 corpus repos exist, the fit is tractable).

### M-5 · `mjolnir-qa-playwright-reporter` is unpublished

## Suggested order

1. **B-2 → B-1 → B-3** — get a working package on npm. Nothing else
   matters while the headline command is broken.
2. **H-4, H-5, H-9, H-7** — four small fixes, each removing a case where
   the tool tells the user something untrue. Highest value per line in the
   catalog.

   means something again.

5. **R-1, R-2, R-3** — stop writing into the scanned repo.
6. **H-3 + P-1** — the deadline and the quadratic blowup are one piece of
   work.
7. **R-4, R-5, R-6, R-7** — the `fix` command, which is the one place a bug
   damages the user's source.
8. **M-1** — the classification backlog; everything in P5 is gated on it.
